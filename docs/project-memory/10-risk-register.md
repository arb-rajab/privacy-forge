| R-08 | The Pest Browser Testing suite (`composer test:e2e`, `tests/Browser/`) hung in Session 16 on a Linux sandbox host, and was assessed there as "environment-specific, not a product regression" pending a check on a different host. That check happened at Session 17, on a genuinely different host (Windows 11 + Docker Desktop/WSL2) — and the hang reproduced with the identical signature, rejecting the "sandbox-specific" hypothesis. **Session 18 made one genuine, targeted attempt at the root cause and the hang did not resolve — reported plainly below, not left ambiguous.** First, Session 17's own proposed mechanism was re-examined by actually reading the relevant source (`vendor/pestphp/pest-plugin-browser/src/Playwright/Servers/PlaywrightNpmServer.php`, `ServerManager.php`), not just re-asserted: the `sh -c` shell Session 17 flagged wraps the PHP→Node launch of `playwright run-server` — it does **not** sit between Node and the Chromium process it subsequently spawns. The actual CDP pipe (fds 3/4) is set up by Node's own direct, shell-free `child_process.spawn()` call when Playwright's already-running Node process launches Chromium — a hop the outer `sh -c` has no way to affect. **This narrows, and partly corrects, Session 17's mechanism theory**: the specific "PHP→Node `sh -c` breaks fd inheritance" story doesn't survive reading the code, even though the *symptom* it was proposed to explain is still real. Second, this session searched Playwright-core's own bundled source (`node_modules/playwright-core/lib/coreBundle.js`) for a documented pipe-vs-WebSocket toggle for a *locally launched* browser — there isn't one exposed via any public Playwright or pest-plugin-browser API; WebSocket-based CDP is only available when *connecting to an already-running remote browser* (`connectOverCDP()`), a fundamentally different usage pattern pest-plugin-browser doesn't use. Switching transport would mean patching Playwright's own bundled internals, ruled out as out of this session's scope (matching Session 17's own reasoning for not patching vendor code). Third, with that route closed, this session made its one concrete attempt at a different, equally well-documented cause of exactly this symptom class: Playwright's own Docker guidance names Docker's default 64MB `/dev/shm` as a common cause of headless Chromium spawning a full process tree and then making no further progress. Added `shm_size: "1gb"` to the `app-e2e` Compose service (the service this session's Dockerfile split — see R-07 below — now uses to run `tests/Browser/`) and re-ran the suite. **Result: unresolved.** Confirmed by process-tree inspection matching Session 17's own method: a full Chromium tree spawned (browser, zygotes, GPU process, network-service utility, two renderers — via `/proc/<pid>/cmdline`), Chromium's own launch args already included `--no-sandbox` and `--disable-dev-shm-usage` automatically (ruling out "missing sandbox/shm flags" as a distinct, separately-fixable variable — Playwright was already applying both), and a clean, bounded 78-second CPU-tick measurement (`/proc/<pid>/stat` fields 14/15, snapshotted before and after a fixed wait, not estimated) showed the browser process's accumulated CPU time grew by only ~20 ticks (~0.2s) — the same near-zero-progress signature Session 17 measured (~8 ticks across several minutes), just re-confirmed on a fresh run with the fix applied. Zero new request/log activity appeared in that window either. | R-07 | Cold Docker image build time on a stranger's first `docker compose up --build` may independently exceed Success Metric #1's 15-minute budget. Session 17 confirmed this directly (2083s/~34.7 min measured on a real cold clone). | Operability | Was Medium (a slow or failed first build is exactly the kind of friction that loses a stranger evaluating this project) | Was Confirmed — a genuinely first-ever cold clone reliably exceeded the 15-minute budget | **Root cause found and fixed, then re-measured.** `docker/Dockerfile` was a single, undifferentiated build stage: the *same* image `docker-compose.yml`'s `app`/`worker` services build and run by default also unconditionally installed Node.js, npm, Playwright, and a real downloaded Chromium (`--with-deps`) — tooling only `pestphp/pest-plugin-browser`'s `tests/Browser/` suite ever uses, never application code at runtime. A stranger running the plain app was paying for browser-testing tooling they would never use. **Fix:** split into a multi-stage Dockerfile — `runtime` (default target, no Node/npm/Playwright/Chromium at all) and `test` (extends the same shared dependency layer with Node/Playwright/Chromium, used only by a new Compose-profile-gated `app-e2e` service: `docker compose --profile e2e run --rm app-e2e composer test:e2e`). **Re-measured with the identical rigour Session 17 used** (`docker compose down`, `docker rmi -f` on all project images, `docker builder prune -af`, confirmed 0B cache/0 images, then a single bracketed `docker compose up --build -d`), on the same class of host (Windows 11 + Docker Desktop/WSL2): **643 seconds (~10.7 minutes)** — a ~69% reduction, now under the 900-second budget on its own. The final `app` image also shrank from ~3.3GB to 1.32GB, consistent with removing that tooling. **One genuine regression found by actually running the tests, not assumed fixed:** the initial split moved `sockets`/`pcntl` (PHP extensions) into the `test` target only, reasoning they're only *used* by `tests/Browser/` — but `pestphp/pest-plugin-browser` hooks into Pest's global test lifecycle at boot regardless of which file runs, so **every** `composer test` invocation (not just the browser suite) failed with `Call to undefined function Pest\Browser\Support\socket_create_listen()` once those extensions were removed from `runtime`. Fixed by keeping `sockets`/`pcntl` in the shared base layer both targets build from — confirmed by directly timing the isolated compile step (**73 seconds**, materially more than this session's own Dockerfile comment first assumed before actually measuring it, corrected in place) and by re-running the full Feature suite (165/165 passing). **Honest gap, stated plainly:** a fresh, fully clean cold-clone timing of the *exact final* Dockerfile (extensions restored) could not be completed this session — repeated full builds in a short window tripped GitHub's anonymous `codeload.github.com` rate limit (a session-specific artifact of this session's own repeated testing, not a repository defect; a real single-attempt clone by an actual stranger would not reproduce this). The fix's *functional correctness* is nonetheless directly confirmed (165/165 tests passing against a live-patched container, sidestepping the rate limit entirely since no package re-download was needed for that check), and the extension-compile step's own real cost (73s) is directly measured, not guessed — so the best-supported estimate for the final Dockerfile's cold-clone time is **643s + 73s ≈ 716s (~11.9 min)**, still comfortably under the 900s budget, though this specific sum has not been confirmed by one single unbroken timed run. Session 16's two build-cache fixes (layer reordering, `worker`'s duplicate build elimination) remain in place and unaffected by this session's stage split.
