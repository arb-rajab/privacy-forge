| R-08 | The Pest Browser Testing suite (`composer test:e2e`, `tests/Browser/`) hung in Session 16 on a Linux sandbox host, and was assessed there as "environment-specific, not a product regression" pending a check on a different host. That check happened at Session 17, on a genuinely different host (Windows 11 + Docker Desktop/WSL2) — and the hang reproduced with the identical signature, rejecting the "sandbox-specific" hypothesis. **Session 18 made one genuine, targeted attempt at the root cause and the hang did not resolve.** First, Session 17's own proposed mechanism was re-examined by actually reading the relevant source (`vendor/pestphp/pest-plugin-browser/src/Playwright/Servers/PlaywrightNpmServer.php`, `ServerManager.php`), not just re-asserted: the `sh -c` shell Session 17 flagged wraps the PHP→Node launch of `playwright run-server` — it does **not** sit between Node and the Chromium process it subsequently spawns. The actual CDP pipe (fds 3/4) is set up by Node's own direct, shell-free `child_process.spawn()` call when Playwright's already-running Node process launches Chromium — a hop the outer `sh -c` has no way to affect. **This narrows, and partly corrects, Session 17's mechanism theory**: the specific "PHP→Node `sh -c` breaks fd inheritance" story doesn't survive reading the code, even though the *symptom* it was proposed to explain is still real. Second, Session 18 searched Playwright-core's own bundled source (`node_modules/playwright-core/lib/coreBundle.js`) for a documented pipe-vs-WebSocket toggle for a *locally launched* browser — there isn't one exposed via any public Playwright or pest-plugin-browser API; WebSocket-based CDP is only available when *connecting to an already-running remote browser* (`connectOverCDP()`), a fundamentally different usage pattern pest-plugin-browser doesn't use. Switching transport would mean patching Playwright's own bundled internals, ruled out as out of scope (matching Session 17's own reasoning for not patching vendor code). Third, with that route closed, Session 18 made its one concrete attempt at a different, equally well-documented cause of exactly this symptom class — Docker's default 64MB `/dev/shm` (Playwright's own Docker guidance names this as a common cause of headless Chromium spawning a full process tree and then making no further progress): added `shm_size: "1gb"` to the `app-e2e` Compose service and re-ran the suite. **Result: unresolved**, confirmed by process-tree inspection (a full Chromium tree spawned, `--no-sandbox`/`--disable-dev-shm-usage` already applied automatically by Playwright, and a clean bounded CPU-tick measurement showing near-zero progress — the same signature as Session 17).
