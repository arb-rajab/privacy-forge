| R-04 | ADR-0003's external chain-anchoring for the audit log has never been implemented — only the hash-chain (entry-level tamper detection) and DB-grant (R-01) layers exist. This is a known, designed-for degradation: ADR-0003 explicitly anticipated "chain-only" as an accepted, weaker state if anchoring is unavailable (see its Consequences section), not an unexpected gap — but it must not be forgotten before it matters. | Security | Medium (the stronger guarantee ADR-0003 describes — protection against an attacker who edits an entry *and* recomputes the chain — is not yet available; entry-level tamper detection alone still holds) | Low today (requires an attacker capable of both editing an entry and recomputing subsequent hashes), rising to a real gap once the product is deployed and relied on as evidence | Hash chain already provides entry-level tamper-evidence independently; a scheduled anchoring job (per ADR-0003's Decision) is the direct fix, and ADR-0003 requires its unavailability to alert rather than fail silently | Open | Now the top-priority open item — see `12-session-handoff.md`'s "Next recommended session" |
| R-07 | Cold Docker image build time on a stranger's first `docker compose up --build` may independently exceed Success Metric #1's 15-minute budget, separate from any application-level timing or connector issues. **Measured this session** with a genuinely cold builder cache (`docker builder prune -f`, reclaiming 11.76GB, then a full `docker compose up --build`): the Playwright/Chromium install layer alone took ~15-18 minutes (two independent measurements this session, ~1069s and ~1069s-equivalent), and one attempted end-to-end cold-build measurement was confounded by an extreme, unexplained host-level stall in this sandboxed session environment (a ~13-hour wall-clock gap between this session's own `date` timestamps bracketing a single `docker compose up --build` call, alongside transient `cdn.playwright.dev` DNS failures and a container-name conflict from a stray concurrent process) — that specific number is not reported as a build-time measurement because it plainly is not one; it reflects this sandbox's own anomalous behaviour, not the Dockerfile. Root cause of the *avoidable* cost, confirmed by reading `docker/Dockerfile` and `docker-compose.yml`: (1) the Playwright/Chromium install step was ordered *after* `COPY . .`, so it re-ran on every rebuild that changed any file in the repo, not only when `package.json`/`package-lock.json` changed; (2) `app` and `worker` each declared their own `build:` block with an identical Dockerfile, so a cold `docker compose up --build` built the same ~15-18 minute layer *twice*, in parallel (confirmed directly this session: a cold build showed two independent `RUN npm ci && npx playwright install` steps, one per service, each paying the full download cost separately). | Operability | Medium (a slow or failed first build is exactly the kind of friction that loses a stranger evaluating this project, independent of anything the application itself does correctly) | High for the *avoidable* half (true for every fresh clone and every `app`/`worker` build, by construction, until fixed) — the *unavoidable* half (downloading ~300MB of Chromium once, on a repo's genuinely first-ever build) cannot be eliminated, only paid once | **Both root causes fixed and verified this session:** (1) `docker/Dockerfile` reordered so `COPY package.json package-lock.json*` + the npm/Playwright install layer happens *before* `COPY . .` — an ordinary code change no longer invalidates that layer. (2) `docker-compose.yml`'s `worker` service no longer has its own `build:` block; it now reuses `app`'s tagged image (`image: privacy-forge-app:latest` on both), so the expensive layer is built at most once per `docker compose up --build`, not twice. **Verified together**, immediately after the cold build above: a subsequent `docker compose up -d --build` with no `package.json`/`package-lock.json` change completed in **165 seconds total** (context transfer + cached composer/npm/Playwright layers + one `composer install` re-run for the changed application code + image export/unpack for both `app` and `frontend`), with only one image ("app") reported as `Building` instead of two. Not attempted: a pre-built image on a registry (`docker compose pull`) — would need a registry/CI publishing step, out of scope this session. | Open | Before deployment, alongside R-04 — a genuinely first-ever clone's *first* build still pays the ~15-18 minute Chromium download once, by construction; that residual risk to Success Metric #1's 15-minute budget is unavoidable without a registry-hosted prebuilt image (not attempted this session) |
| R-08 | The Pest Browser Testing suite (`composer test:e2e`, `tests/Browser/`) hung indefinitely this session on this specific sandboxed host, after previously passing reliably in Sessions 14-15 on (presumably) different host infrastructure — could not be run to completion despite four independent attempts (killing stray leftover processes from earlier interrupted runs, a full `app` container restart, disabling TTY allocation on `docker compose exec`, and running `vendor/bin/pest` directly instead of through the `composer test:e2e` wrapper). Diagnosis performed this session: the hang occurs *before* any page navigation is ever attempted (zero `GET`/`POST` entries appear in the app container's request log across every attempt, even after 10+ minutes); a real headless Chromium process is genuinely launched and stays resident (confirmed via `/proc`) but sits idle at ~0% CPU with essentially no accumulated CPU time, consistent with a stalled handshake between Playwright/Pest's browser driver and the launched Chromium rather than a slow-but-working test. Not caused by this session's own code changes — every new file this session is a new backend route/config/seeder with zero relationship to the widget, DSAR portal, admin dashboard, or login pages the browser tests exercise, and the *Feature* suite (which does exercise the ABAC/connector/DSAR business logic these browser tests also cover, including two new tests proving the R-06 fix) passes cleanly (160/160). | Operability (test infrastructure) | Medium — blocks running the one test suite that proves Success Metric #1's UI-only, zero-DevTools claim end-to-end; does not indicate any actual product regression, since the Feature suite and a real manual curl-driven walkthrough (this session, see `12-session-handoff.md`) both independently exercise and confirm the same underlying business logic | Unknown until reproduced on a different host — could be specific to this sandbox's virtualization stack (Windows Docker Desktop + WSL2 backend), a stale Playwright/Chromium cache artifact from this session's from-scratch image rebuild, or an actual upstream compatibility issue | A future session should first confirm whether this reproduces on a clean host/checkout before investigating further; if it does not reproduce, this was environment-specific to this session and can be closed without a code change | Open | Before relying on `composer test:e2e` again — check this first, before attributing any future browser-test failure to a code change |
