| ID | Risk | Category | Impact | Likelihood | Mitigation | Status | Review date |

| R-01 | Audit log lacks DB-level grant revocation (ADR-0003) — app's Postgres role owns the table, so privileges can't be revoked from itself | Security | Medium | Low (requires DB credential compromise) | Hash chain still provides tamper-evidence independently; needs a second, lower-privileged migration-only DB role to fully implement | Open | Before Session 8 (deployment) |
| R-02 | No seeding/bootstrap mechanism exists for `PolicyDefinition` rows — a fresh instance has no active `dsar.identity.verify`, `dsar.erasure.approve`, `policy.update` (Session 10), `retention.policy.manage` (Session 11), or `ropa.export` (Session 12) policy until each is inserted manually. **Re-verified Session 13, gap is 0 of 5 policies covered, unchanged from Session 12**: `database/seeders/` exists as an empty directory (a leftover default Laravel scaffold path, not a real bootstrap) — it is untracked by git (`git ls-files database/seeders` returns nothing) and contains no `DatabaseSeeder.php` or any seeder class anywhere in the repository. The only place any of the five `PolicyDefinition` rows are constructed is `database/factories/PolicyDefinitionFactory.php`, which is test-only scaffolding, never invoked outside `tests/`. So all five sensitive actions (`dsar.identity.verify`, `dsar.erasure.approve`, `policy.update`, `retention.policy.manage`, `ropa.export`) still require manual row insertion on a fresh instance. | Operability | Low (fails safe, not open — ADR-0006 fail-closed denies everyone rather than granting access; this is an availability/usability gap, not a security exposure) | High (true on every fresh install by default) | None yet; a `database/seeders/` bootstrap remains the most direct fix | Open | Before deployment |
| R-04 | ADR-0003's external chain-anchoring for the audit log has never been implemented — only the hash-chain (entry-level tamper detection) and DB-grant (R-01) layers exist. This is a known, designed-for degradation: ADR-0003 explicitly anticipated "chain-only" as an accepted, weaker state if anchoring is unavailable (see its Consequences section), not an unexpected gap — but it must not be forgotten before it matters. | Security | Medium (the stronger guarantee ADR-0003 describes — protection against an attacker who edits an entry *and* recomputes the chain — is not yet available; entry-level tamper detection alone still holds) | Low today (requires an attacker capable of both editing an entry and recomputing subsequent hashes), rising to a real gap once the product is deployed and relied on as evidence | Hash chain already provides entry-level tamper-evidence independently; a scheduled anchoring job (per ADR-0003's Decision) is the direct fix, and ADR-0003 requires its unavailability to alert rather than fail silently | Open | Before Session 8 (deployment), alongside R-02's seeder work and the Demo Instance Data Safety controls in `06-security-threat-model.md` — all deployment-phase work |
| R-06 | No connector in v1 has a real, working webhook receiver — ADR-0004 deliberately scopes connectors as external, third-party-operated services, so nothing in this repository listens on any `webhook_url`. Found this session while manually stopwatch-verifying the README's 15-minute walkthrough end to end: the README's own step-0 tinker snippet creates a `Demo Connector` pointed at `https://example.test/webhook` (a placeholder nothing answers), so `DispatchConnectorTaskJob` genuinely retries with backoff (15s/30s/60s/120s, ~3.75 minutes total against the default `CONNECTOR_WEBHOOK_MAX_RETRY_ATTEMPTS=5`) and then genuinely fails every single time a fresh instance is walked through exactly as documented. `DsarCompletionEvaluator` then correctly settles the DSAR at `partially_complete`, not `complete` — the README previously claimed `complete`, now corrected (this session) to describe the real, honest outcome. A deletion certificate is still produced either way (FR-011), so the DSAR half of the cycle is still genuinely real; only the exact status word was wrong. Separately (and unrelated to this specific finding — a local dev-environment artifact, not a code issue), this session's `docker compose ps -a` also found the `worker` container itself `Exited (1)` for hours before this session began, apparently stale since before `barryvdh/laravel-dompdf` was added — worth a rebuild if a future session needs the queue worker running. | Operability | Low (the delay is wasted time and an inaccurate status word, not a security exposure or data-integrity risk — fail path is correctly handled and disclosed) | High (true on every fresh self-hosted install that follows the README exactly, by construction) | A future session (naturally paired with R-02's demo-instance/seeder work, since that will need a genuinely working demo connector anyway) could add a minimal built-in stub webhook receiver, or point the README's demo connector at one that actually responds 200 | Open | Alongside R-02 |

| R-03 | ADR-0006 commits to `policy.update` as a gated, audited sensitive action. Session 9's NFR-005 matrix found no controller/route implemented this — policies were only editable via CLI/seeders, a documented-but-unimplemented control rather than an active vulnerability. | Security | Was informational/low; would have become a real gap the moment an ungated policy-editing endpoint shipped | N/A (control gap, not an active exploit path) | Session 10 built `GET /admin/policies`, `GET /admin/policies/{id}`, and `PATCH /admin/policies/{id}` (`App\Http\Controllers\Admin\PolicyController`), all three gated by a real `policy.update` `PolicyEvaluator::evaluate()` call — Owner-only, audit-logged, fail-closed (both `policy_missing` and `evaluation_error` reason codes tested). Added to `AuthorisationMatrixTest.php`'s dataset (now 3 actions, 15 cells) and covered by a dedicated `tests/Feature/PolicyManagementTest.php`. All 110 tests pass, Pint clean, Larastan level 8 clean. | **Closed** | Session 10 (2026-08-15) |
| R-05 | No staff authentication (login/session) existed. Every sensitive action was reachable only via test harness (`actingAs()`) or shell access (`php artisan tinker`), never a real HTTP session — blocking genuine use of the product and leaving T-11/T-12/T-13 untested against anything real. Highest-priority open item at the time it was added. | Security / Operability | Was High (nobody could actually use the product as a real staff user) | Was Certain (true on every install by construction) | Built real session-based login: `App\Http\Controllers\Auth\AuthenticatedSessionController` (`GET/POST /login`, `POST /logout`), a Vue `Login.vue` page matching the existing house style, and `php artisan privacy-forge:create-owner` to bootstrap the first Owner account without shell access to application code. Session regenerates on login and is fully invalidated (guard cleared, session invalidated, token rotated) on logout (T-11) — `tests/Feature/LoginRateLimitTest.php`. Rate-limiting is hand-rolled against the cache rather than `RateLimiter::hit()`, whose decay argument only takes effect on a key's first call — each further failed attempt at least doubles the lockout window (capped at 5 minutes), and unknown-email/wrong-password produce the identical generic message (T-13) — same test file. CSRF (T-12) was verified with a real test that defeats Laravel's `runningUnitTests()` CSRF bypass (which silently exempts every ordinary Pest test, including every pre-existing `actingAs()`-based test in this suite) — `tests/Feature/CsrfProtectionTest.php` proves a state-changing admin request is rejected (419) without a token and succeeds with one. `tests/Browser/DsarLifecycleTest.php`'s admin steps now authenticate via real `POST /login` calls (session cookie captured and forwarded by hand, since Laravel's test client doesn't do this automatically) instead of `actingAs()`; a new `tests/Browser/StaffLoginUiTest.php` drives the actual Login.vue form in a real Playwright browser. **Correction to this session's own brief:** `App\Models\User` (with its `role` enum, factory, and `isPrivilegedFor()` helper) and its migration already existed prior to this session — confirmed the role representation (`owner`/`privacy_manager`/`support_staff` lowercase strings) already matches exactly what `PolicyEvaluator` and all five registered policies expect, so no changes were needed there; only the login/logout/bootstrap layer around it was missing. | **Closed** | Session 14 (2026-08-18) |
