| R-07 | Cold Docker image build time on a stranger's first `docker compose up --build` may independently exceed Success Metric #1's 15-minute budget, separate from any application-level timing or connector issues. **Re-measured this session (Session 17) on a genuinely different host** (Windows 11 + Docker Desktop/WSL2, vs. Session 16's Linux sandbox) — this was the specific number Success Metric #1 depends on, not the repeat-rebuild number, and Session 16 could not obtain it cleanly. A second, previously unmeasured and unreported cost specific to this host's containerd image store: **exporting and unpacking the final ~3.3GB `app` image took 348.7s (~5.8 min) on its own** (`exporting layers 209.2s` + `unpacking ... 138.5s`) — roughly as expensive as the Chromium download itself, and not something either of Session 16's two fixes touches. The remaining ~1266s went to steps not captured in the retained log tail (initial `apt-get`/nodesource/Node install, the first `composer install`, and the separate `frontend` image's own `npm install`) — not broken down further this session, but real and included in the 2083s total. | Operability | Medium (a slow or failed first build is exactly the kind of friction that loses a stranger evaluating this project, independent of anything the application itself does correctly) | **Confirmed, not just suspected, this session: a genuinely first-ever cold clone reliably exceeds the 15-minute budget** (2083s measured directly) | **Session 16's own two fixes were re-verified as correctly structural, not just cache-dependent, this session** — see `12-session-handoff.md`'s "Part A" section for the full reasoning. (2) Eliminating `worker`'s duplicate `build:` block helps *both* repeat builds *and* the first-ever cold build — this session's own build log confirms `worker` triggered zero build steps of its own (it only referenced `app`'s already-built tag), whereas Session 16 had directly observed the pre-fix code running the same ~15-18 minute layer twice, in parallel, on a cold cache specifically (not just on a cache-invalidating rebuild). This was not re-confirmed by reverting the fix and re-measuring the old buggy behaviour side-by-side this session (would have meant deliberately reintroducing a closed defect purely to benchmark it) — the structural reasoning plus Session 16's own direct log observation is treated as sufficient evidence. | R-08 | The Pest Browser Testing suite (`composer test:e2e`, `tests/Browser/`) hung in Session 16 on a Linux sandbox host, and was assessed there as "environment-specific, not a product regression" pending a check on a different host. **That check happened this session (Session 17), on a genuinely different host (Windows 11 + Docker Desktop/WSL2) — and the hang reproduced with the identical signature**: `docker compose exec -T app vendor/bin/pest tests/Browser -v` launched a real, full Chromium process tree (browser, zygotes, GPU process, network-service utility, and two renderer processes — confirmed via `/proc/<pid>/cmdline`, a fuller tree than Session 16 reported reaching), but zero `GET`/`POST` navigation requests ever appeared in the app container's log across 12+ minutes, and the browser process's own accumulated CPU time (`/proc/<pid>/stat` fields 14/15) grew by only ~8 ticks (~0.08s) across several minutes of wall-clock time — a stalled handshake, not a slow-but-working test, exactly as Session 16 characterised it. **This upgrades the assessment: the hypothesis that this was specific to Session 16's own sandbox is now rejected by direct evidence, not merely unconfirmed.** A concrete, plausible (not proven) mechanism was identified this session by reading the actual process tree: Playwright launches Chromium with `--remote-debugging-pipe` (CDP over inherited file descriptors 3/4, not a TCP/WebSocket port), and the launch chain observed is `pest` (PHP) → `sh -c './node_modules/.bin/playwright run-server ...'` → `node` → `chromium` — the intermediate `sh -c` shell is a well-known point where exact fd 3/4 inheritance can silently break across process layers, which would produce exactly this symptom (a real process launches, but the CDP pipe handshake never completes because neither side is actually connected to the fds the other expects). This is Playwright/Pest-plugin-browser's own launch behaviour, not something any application-code session (including Session 16) introduced, and this session did not attempt to patch vendor code to confirm or fix it — that would be a different, larger undertaking than this session's scope. **Substituted with a real, honest manual walkthrough this session** (see `12-session-handoff.md`, "R-08 manual walkthrough") — the specific claims from Sessions 14/15 were re-checked one at a time: real `/login` with real CSRF/session cookies (works), the real `verify-identity` endpoint the "Verify identity" button calls (works, moves the DSAR to `in_progress`), the real ADR-0007 separation-of-duties denial when the same admin tries to approve (works, real 403), a second real admin's real `approve-erasure` call (works), and the DSAR reaching real `status: complete` via the actual async worker/reference-connector round trip (confirmed directly against the database). The Vue component source (`resources/js/Pages/AdminDsarQueue.vue`) was also read directly and confirmed its `verifyIdentity()`/`approveErasure()` handlers call exactly these same two endpoints. **What this walkthrough does not and cannot confirm, stated plainly**: that a real browser actually renders these buttons and that a real mouse click actually fires those handlers — Inertia's server-rendered HTML for `/admin/dsar` carries no queue data in its initial payload (confirmed by inspecting the raw `data-page` JSON; the queue list is fetched client-side after Vue mounts), so a curl-only check structurally cannot observe the rendered DOM. That specific gap is exactly what the hung suite would have proven and is the one part of Sessions 14/15's claims that remains genuinely unconfirmed this session. | Operability (test infrastructure) | Medium — blocks the one test suite that proves Success Metric #1's UI-only, zero-DevTools claim end-to-end via real DOM interaction; the backend contract those buttons depend on is now independently re-confirmed against a live stack post-Session-16, so the risk is narrower than "the buttons might not work," but the gap to "a real click was proven to fire them" is real and not closed | Confirmed to reproduce across two independent, unrelated host environments with an identical signature — no longer "unknown," now assessed as a likely structural Playwright/Pest-plugin-browser CDP-transport-vs-process-layering issue, not a per-sandbox fluke | A future session could try forcing a non-pipe CDP transport (if pest-plugin-browser/Playwright exposes one) or reproducing the hang with a minimal standalone Playwright script (no Pest/Laravel involved) to isolate whether Pest's own process launching is implicated or whether it's Playwright-in-Docker generally; until then, the manual-walkthrough pattern established this session is the fallback for re-confirming button-driven claims after future changes | Open | Before next relying on `composer test:e2e` for a release gate — this is no longer expected to "just work on a different host" |

| R-04 | ADR-0003's external chain-anchoring for the audit log had never been implemented — only the hash-chain (entry-level tamper detection) and DB-grant (R-01) layers existed. A known, designed-for degradation (ADR-0003 explicitly anticipated "chain-only" as an accepted, weaker state), not an unexpected gap — but a real one until closed. | Security | Was Medium (the stronger guarantee ADR-0003 describes — protection against an attacker who edits an entry *and* recomputes the chain — was not available; entry-level detection alone still held) | Was Low today, rising over time as the product is deployed and relied on as evidence | Built `AuditLogger::anchorChain()`/`verifyAnchors()` and two commands: `audit:anchor-chain` (scheduled hourly, `routes/console.php`) and `audit:verify-chain` (the runbook item ADR-0003's Consequences section explicitly calls for). Anchors are written to the existing `s3` disk (the same external object storage export bundles already use — no new infrastructure dependency), one immutable-by-construction object per anchored sequence (`audit-anchors/{sequence}.json`), never overwritten — deliberately *not* stored in this application's own Postgres database, since a DB-stored anchor would be exactly as editable by the attacker ADR-0003's threat model assumes as the entries themselves, defeating the point. **Proven with real evidence, not just an assertion the code runs** (`tests/Feature/AuditChainAnchorTest.php`): the key test builds a real 3-entry chain, anchors it, then simulates a genuinely privileged DB-access attacker — bypassing `AuditLogEntry`'s append-only guard via `DB::table()->update()` (the same technique `ConsentCaptureTest.php` already uses) — tampering with the *first* entry and correctly recomputing every subsequent `prev_hash`/`entry_hash` so the chain is internally consistent again. `verifyChain()` alone is fooled (`valid: true`) — proving the exact gap ADR-0003 describes. `verifyAnchors()` is not: it detects the mismatch at the anchored sequence, because the anchor written *before* the tampering still holds the *original* hash.
